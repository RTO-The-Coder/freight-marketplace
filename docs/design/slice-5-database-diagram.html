Drivers independent Drivers have real identity and are referenced (by DriverAssignment, and by two Tracking tables), not duplicated.

Shippers independent Pure identity — Id, Name, ContactEmail. Pulled forward from its originally-planned later slice so a posted Shipment has a real, DB-backed owner now rather than later.
Shipments independent, aggregate root Id/pickup/delivery/cargo, plus a real ShipperId foreign key. No state machine or deadline yet — those arrive in a later slice. Location and cargo size are owned value objects, inlined as columns.
DriverComplianceStates independent One row per Driver — DriverId is the primary key directly, no separate surrogate id, with a real foreign key to Drivers (ON DELETE CASCADE). Carries an in-memory-only DomainEvents collection that's explicitly excluded from the mapping, not a column.
RouteProgresses independent One row per Truck, TruckId is the primary key directly. Carries both CurrentLegIndex and TicksElapsedInCurrentLeg (an earlier draft of this diagram was missing the latter — corrected).
RouteLegs independent One row per leg of a truck's route (composite key: TruckId, LegIndex), holding the raw OSRM-derived driving duration for that leg, rounded up to the 10-minute grid. Deliberately stores pure driving time, not a rest-adjusted figure — position/percentage-along-leg is meant to be computed live from this plus the driver's actual driving-minutes-elapsed, never stored as a column. A separate table rather than a single field on RouteProgresses specifically so a route's leg durations can be computed up front at route-assignment time and survive the truck advancing past earlier legs — needed for whole-route feasibility checks and mid-route shipment insertion. The schema/storage exists; the OSRM client and calculation logic that populate and read it do not (see open issues below).
DriverRulePreferences independent One row per Driver, plain scalar fields, no complications — the simplest table in the model. FK to Drivers.Id is ON DELETE CASCADE — a driver's preferences have no meaning once the driver is gone. The repository that reads this table at runtime doesn't exist yet (see open issues below).

Non-obvious mapping decisions

Why DriverAssignment got its own table

It was designed with no identity of its own — only reachable via DriverAssignment.Single(driver) / .Team(first, second), never a bare constructor. EF Core's constructor-binding convention rejected mapping it as a pure owned/inline value: two of its three constructor parameters are references to Driver, an independent entity, and EF's materializer can only auto-bind scalar or owned-value parameters through a constructor — never references to another entity's row. Confirmed empirically (tried as an owned type first, failed identically whether owned or promoted to independent, until the actual root cause — the missing constructor — was fixed), not assumed from documentation alone.

Why the foreign key sits on Truck, not DriverAssignment

The natural phrasing — "a DriverAssignment belongs to a Truck" — would put TruckId on the DriverAssignment row. EF Core rejected that direction: Truck is itself owned by TruckingCompanies, and an owned entity cannot be the principal side of an unrelated (non-ownership) relationship. Flipping it — Truck.DriverAssignmentId referencing DriverAssignment.Id — is what actually migrated and applied cleanly.

Small, deliberate domain-model changes required

Truck, DriverAssignment, TruckCapacity, Shipment, and DriverComplianceState each needed a private parameterless constructor added, used exclusively by EF Core's reflection-based materializer when reloading a row. No public construction path changed — TruckingCompany.RegisterTruck(...) and DriverAssignment.Single(...)/Team(...) remain the only ways application code can construct these types.

InternalsVisibleTo was deliberately not extended

EF Core's materializer invokes non-public constructors and sets private-set/backing fields via reflection, bypassing C#'s compile-time accessibility checks entirely — so no new assembly needs compile-time access to Domain's internals for persistence to work.

Explicitly not a table

RestRuleLimits

Pure configuration record (EU-561/2006 numeric limits), no identity, used only as a method parameter. A DB-backed loader is a separate, undesigned feature.

DriverRulePreferenceRegistry

A pure in-memory Dictionary lookup, never persisted itself. A future slice may add a repository that populates one from the real table at runtime.

Capacity / GeoCoordinate / TruckCapacity

Owned value objects, inlined as plain columns on their owner (Truck, Shipments) — not separate tables.
